## Packaging and handoff findings

### Historical format — M6.12ap

Preserved TB-8704F artifacts establish a historical Android boot-image v0
convention: 2048-byte pages, a gzip kernel payload containing the appended
DTB (`dt_size=0`), and a ramdisk. The restored `mkbootimg-h4.6` can also encode
a separate DT segment, but the inspected historical images did not use that
option. This is artifact-layout evidence only; it does not prove acceptance of
a new Linux 6.12 image or its DTB by the target loader.

### Physical placement — M6.12aq

The inspected Linux 6.12 ARM64 `Image` has `text_offset=0` and
`image_size=0x02cc0000`. ARM64 requires a 2 MiB-aligned image base with that
range available. Historical TB-8704F package metadata gives a kernel address
of `0x80008000` and ramdisk address `0x81000000`; if interpreted as literal
placement for this candidate, the kernel address is misaligned and the
ramdisk overlaps the candidate image range. The actual loader relocation and
decompression behavior is unknown, so this is a static compatibility conflict
conditional on those addresses being literal—not a runtime observation.

**Do not reuse the historical address tuple for a new package** until a
loader/source/trace contract establishes final kernel, initrd, and DTB
placement. No such contract is currently recorded.

### Compressed payload compatibility — M6.12at

Linux 6.12 ARM64 does not provide a decompressor: its boot protocol requires
the boot loader to decompress `Image.gz`. Kbuild's generic `Image.gz` target is
gzip applied to `Image`; it is not a self-decompressing zImage, and Kbuild has
no generic `Image.gz-dtb` target. Compression therefore does not by itself
resolve the historical kernel-address mismatch or prove that the loader will
pass the appended DTB in the required ARM64 handoff. The historical TB8704
gzip-plus-DTB byte layout remains packaging evidence only.

### Initramfs and capacity — M6.12an, M6.12x, M6.12y

- M6.12an produced a validated archive-only diagnostic initramfs. At that
  phase it was not embedded in a kernel; runtime execution and target handoff
  remain unproven, and it is not a root userspace.
- **Updated by M6.12ar:** an isolated generic Linux 6.12 ARM64 `Image` now
  embeds the hardened M6.12an archive. This avoids a separately placed initrd
  for that candidate, but does not prove that the tablet loader accepts the
  standalone `Image`, provides its DTB, or places the kernel at a valid address.
  The embedded userspace remains diagnostic-only.
- Preserved evidence supports eMMC at SDHCI `7824900` and Android mounting
  `/system` from that controller. It does not establish a Linux 6.12 `root=`
  policy or init/root transition.
- A later static size comparison put a generic `Image`, candidate DTB, and
  preserved recovery ramdisk comparator below the recorded 64 MiB partition
  capacity. The ramdisk was only a comparator; no final candidate image was
  assembled and this does not establish format, placement, or bootability.

## Gate and allowed scope

**Current result:** source scaffold and offline evidence are retained; target
loader/header acceptance, final physical placement, DTB/initrd handoff, a
complete board configuration, and mainline root policy remain **NOT PROVEN**.
The candidate must be treated as partial and non-bootable.

Safe offline source review and documentation may continue. Do not build a boot
package using guessed physical addresses. The owner now permits non-destructive
ADB/Fastboot inspection/control, reboot, and temporary `fastboot boot`, but
prohibits flashing, erasing, formatting, partitioning, unlocking, or persistent
device modification. Stop for owner assistance if Android/recovery requires an
unlock code or the device is blocked/unauthorized/offline/ambiguous. This
permission does not resolve the candidate's load-address/DTB-handoff gaps or
make it bootable.

Detailed phase reports and artifact hashes remain in the coordinating
workspace under `mainline/build/m612*/`; those build records are not copied
into this source repository.
